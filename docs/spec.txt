The Met: Hidden Treasures

Full Technical & Product Specification

Version: 2.0 Purpose: Implementation handoff for Claude / coding agent

------------------------------------------------------------------------

1.  Product Overview

Build a polished, mobile-first web app for a children’s scavenger hunt
inside The Metropolitan Museum of Art in New York City.

Working title:

THE MET: HIDDEN TREASURES

Target users: - Children approximately 8–10 years old - Primarily played
on a parent’s smartphone - English-speaking - Played physically inside
The Met while walking from gallery to gallery

Core concept:

The child visits a sequence of museum galleries. In each gallery, the
app presents a short rhyming riddle describing a small, easily
overlooked detail hidden inside one artwork.

The riddle must NOT initially reveal: - artist - artwork title - image
of the artwork - exact location of the object

The child searches the physical gallery, finds the artwork/detail,
photographs it with the mobile device, and uploads/submits the photo to
the app. AI vision verifies whether the intended artwork/detail has been
found.

After a successful discovery, the app reveals the artwork, celebrates
the find, adds the treasure to the child’s collection, and uses a
simplified museum map to direct the player to the next gallery.

The experience should feel like a physical museum treasure hunt, not an
educational quiz.

Primary game loop:

CLUE → LOOK UP → SEARCH → FIND → SNAP → VERIFY → CELEBRATE → MAP → WALK
→ NEXT CLUE

The website must never become more interesting than the museum. The
phone should prompt the child to look at real art, then get out of the
way.

2.  Core Product Principles

3.  Physical discovery comes first.

4.  Minimize screen time while the child is searching.

5.  Do not show the target artwork before the child finds it.

6.  Photo verification is the primary answer mechanism.

7.  AI failure must never trap the child.

8.  No account is required.

9.  Do not request GPS/location permission.

10. Do not permanently store children’s submitted photographs by
    default.

11. The museum map is a navigation aid, not indoor GPS.

12. Core riddles, progress, and map should remain usable when
    connectivity is weak.

13. Keep educational information short and optional.

14. Design for children without making the visual design childish.

8.  Photo Capture

Photo verification is the primary answer mechanism.

On supported mobile browsers, allow the child to open the rear camera
using a standard image file input, for example:

Also permit choosing an existing image from the photo library where
supported.

Do not request camera access on page load.

Only invoke the camera/photo picker after the user explicitly taps the
photo button.

After capture, display a preview:

IS THIS YOUR TREASURE?

[photo preview]

USE THIS PHOTO RETAKE

If practical, allow crop/zoom before submission because the hidden
detail may occupy a small portion of the painting.

Do not instruct the child to physically approach the artwork more
closely.

Prefer language such as:

“Zoom with your camera if the treasure is tiny.”

Do not encourage flash.

If camera access fails or permission is denied, offer:

CHOOSE A PHOTO CONTINUE WITHOUT PHOTO

The entire game must remain usable without camera permission.

------------------------------------------------------------------------

9.  Photo Processing

Before upload, where practical: - resize very large photographs
client-side - compress the image to a reasonable upload size - normalize
orientation - remove EXIF metadata, including location metadata

Do not store image blobs in localStorage.

Do not permanently retain uploaded images by default.

10. AI Photo Verification

Use a multimodal vision model/API to verify discoveries.

The goal is not merely to identify the painting.

The verifier should determine:

1.  Is the submitted photograph plausibly of the intended artwork?
2.  Is the target hidden object/detail visible?
3.  Is there sufficient confidence to accept the discovery?

Accept either: - a photograph of the whole artwork where the detail is
reasonably visible, or - a close-up of the hidden detail where enough
context exists to associate it with the intended artwork.

Do not require perfect framing.

The verifier must be quest-specific.

Do NOT use a generic prompt such as: “Does this photo contain the
answer?”

Each quest has its own expected artwork, hidden detail, and visual
verification description.

------------------------------------------------------------------------

11. Verification Response Schema

Server should normalize the vision model response into structured data
such as:

type VerificationResult = { status: | “verified” | “likely” |
“not_found” | “uncertain” | “invalid_image”;

artworkMatch: boolean | null; detailMatch: boolean | null; confidence:
number; feedback: string; };

Do not expose numerical confidence scores to children.

Validate model output server-side before returning it to the client.

13. Manual/Fallback Verification

Photo verification is preferred, but the game must have graceful
fallback modes for: - poor museum connectivity - camera permission
denied - unsupported browser - AI uncertainty - child/parent preference

Fallback options may include: - grown-up confirmation - optional
multiple-choice verification - reveal-answer flow after explicit
confirmation

Multiple choice is NOT the primary game mechanic.

If used, it is a fallback only.

------------------------------------------------------------------------

14. Photo Privacy and Child Safety

This is a children’s product. Use data minimization by default.

Submitted photographs should be used only for immediate answer
verification.

Default lifecycle:

1.  captured/selected locally
2.  resized/compressed locally where practical
3.  EXIF removed where practical
4.  sent securely to verification endpoint
5.  analyzed
6.  discarded after verification

Do not: - permanently store submitted photos by default - build a
server-side child photo gallery - identify people in photographs -
perform facial recognition - collect child names - collect child email
addresses - collect GPS coordinates - use submitted photos for
advertising - use submitted photos for model training

If a photograph includes a person, the verification system should ignore
personal identity and focus only on the artwork/detail.

Include a concise parent-facing privacy explanation.

15. Museum Map

The app must include a visual map focused on the portion of The Met
containing the scavenger-hunt galleries.

Use The Metropolitan Museum of Art’s current Floor 2 map as the
authoritative spatial reference for gallery relationships.

The relevant section is the 19th- and Early 20th-Century European
Paintings and Sculpture area.

Hunt galleries:

810 → 815 → 816 → 817 → 818 → 819 → 821 → 822 → 824 → 825

Nearby galleries may be shown for orientation but should be visually
subdued.

Do not invent gallery relationships.

Verify the current official museum map before finalizing the schematic.

------------------------------------------------------------------------

16. Map Asset and Copyright Approach

Do NOT simply screenshot, trace mechanically, or reproduce The Met’s
published visitor map unless explicit permission/license allows that
use.

Preferred approach:

1.  Consult the current official Met Floor 2 map as a spatial/navigation
    reference.
2.  Create an original simplified SVG schematic of only the relevant
    gallery area.
3.  Preserve useful approximate room relationships and actual
    traversable connections.
4.  Remove unnecessary architectural detail.
5.  Emphasize the 10 game galleries.
6.  Show surrounding galleries only as needed for orientation.

The result should feel like a playful treasure map based on the gallery
layout, not an architectural reproduction.

Include a discreet external action:

OPEN THE MET’S OFFICIAL MAP ↗

Use the current official Met URL, not a hard-coded obsolete PDF if a
maintained interactive map is available.

Treat the following gallery assignments, artworks, hidden details, and

Hidden object: Monocle

26. Visual Design

The experience should feel: - sophisticated - playful -
museum-inspired - adventurous - elegant - appropriate for 8–10-year-olds
without looking preschool-oriented

Avoid: - generic SaaS styling - loud primary-color children’s-app
design - cartoon museum clichés - clutter - excessive animation - tiny
text

Suggested visual language: - warm ivory/paper background - charcoal
text - deep burgundy - muted museum gold - dark forest green accent -
subtle paper/archive/map texture - museum-label-inspired cards -
restrained treasure/detective motifs

Riddle cards can resemble elegant museum clue cards.

------------------------------------------------------------------------

27. Typography

Suggested pairing:

Headlines/riddles: Cormorant Garamond, Libre Baskerville, or similar
elegant serif

Interface: Inter, DM Sans, or similar clean sans-serif

Minimum body text: 16px

Riddle: approximately 24–30px on mobile

Gallery number should be immediately visible and easy to scan while

32. Quest Data Architecture

Do NOT hard-code quest-specific content into UI components.

Use a structured data file such as:

data/quests.ts

Example:

interface Quest { id: number; gallery: string;

artist: string; artwork: string; year?: string;

hiddenObject: string;

riddle: [string, string]; hints: [string, string];

verificationDescription: string;

imageUrl?: string; metObjectUrl?: string; metObjectId?: number;
openAccess?: boolean;

fact?: string;

map?: { x: number; y: number; }; }

Map x/y values represent coordinates in the original schematic/SVG
coordinate system, NOT GPS coordinates.

Separate public pre-solve content from sensitive answer/verification
data where useful so the browser does not unnecessarily receive every
answer before it is needed.

33. Verification Backend

Suggested endpoint:

POST /api/verify

Input: - questId - uploaded image

The server retrieves the expected quest target internally.

Do not trust an expected answer supplied by the client.

Server-side verification target:

interface VerificationTarget { questId: number; artist: string; artwork:
string; hiddenObject: string; verificationDescription: string;
referenceImages?: string[]; }

The model should return structured JSON.

Server must: - validate file type - enforce reasonable file-size
limits - normalize/process images safely - reject malformed requests -
validate model response schema - avoid logging raw image payloads where
possible - discard uploaded image after processing by default -
rate-limit endpoint sufficiently to prevent abuse/cost runaway

------------------------------------------------------------------------

34. Progress Persistence

Use localStorage for MVP progress.

Example:

interface GameProgress { gameStarted: boolean; currentQuest: number;
completedQuests: number[]; hintsUsed: Record<number, number>; attempts:
Record<number, number>; verificationMethod: Record< number, “ai-photo” |
“grown-up” | “manual” >; }

Do not store submitted photo blobs in localStorage.

On refresh/reopen, resume the hunt.

Provide a Start Over action in parent/settings UI.

Require confirmation before deleting progress.

35. Offline / Weak Signal Behavior

Museum connectivity may be unreliable.

After initial load, these should remain usable: - quest riddles -
hints - map - progress - navigation - completed treasure metadata
already available locally

AI photo verification requires connectivity unless a future local model
is implemented.

If verification cannot reach the server:

NO SIGNAL? NO PROBLEM.

“A grown-up can check your discovery.”

Offer:

TRY AGAIN GROWN-UP CHECK ✓

Consider PWA support and caching of: - application shell - quest data
appropriate for client exposure - map SVG/assets - icons/fonts where
permitted - legally usable reveal images

Do not make a network request necessary merely to move between quest
screens.

39. Security and Cost Controls

Because the app accepts image uploads and invokes a paid AI endpoint:

Implement: - image MIME/type validation - upload size limits -
server-side rate limiting - basic abuse protection - structured-output
validation - request timeout handling - graceful AI failure states - no
API secrets in client bundle

Do not allow arbitrary user prompts to be forwarded to the vision model.

The verification prompt should be generated server-side from known quest
data.

------------------------------------------------------------------------

40. Privacy Copy

Include concise parent-facing language explaining:

-   Photos are used to check whether the child found the scavenger-hunt
    detail.
-   Photos are not intended to be permanently stored.
-   The game does not require the child’s name, email, or GPS location.
-   The game does not perform facial recognition.
-   Players should avoid photographing other museum visitors.
-   AI verification can be wrong; grown-up verification is always
    available.

Final production privacy language should reflect the actual deployed
infrastructure and data practices, not merely this design intention.

41. Future Quest Packs

Design the application so the current hunt is one “quest pack,” not the
only possible game.

Future packs might cover: - Egyptian Art - Arms and Armor - American
Wing - Greek and Roman Art - other museum routes

Architecture should allow a future structure such as:

interface QuestPack { id: string; title: string; museum: string; floor?:
string; description: string; questIds: number[]; mapAsset: string; }

Do not build future packs now, but avoid architecture that makes them
difficult.

  ---------------------------------------------
  A. QUEST ORDER IS NOT PHYSICAL CONNECTIVITY
  ---------------------------------------------

Canonical quest order:

1.  Gallery 810
2.  Gallery 815
3.  Gallery 816
4.  Gallery 817
5.  Gallery 818
6.  Gallery 819
7.  Gallery 821
8.  Gallery 822
9.  Gallery 824
10. Gallery 825

This list controls game sequence ONLY.

Never assume that consecutive quest galleries share a doorway.

Never infer a doorway because: - gallery numbers are consecutive; -
rooms look close on a schematic; - rooms share a wall; - one quest
follows another.

A shared wall does not imply a doorway.

HARD CONSTRAINT:

Gallery 817 and Gallery 818 MUST NOT be modeled as directly connected.

questOrder may contain:

817 → 818

but galleryConnections MUST NOT contain:

817 ↔ 818

The Quest 4 → Quest 5 transition must use the actual intervening public
circulation route verified from the current Met map or by on-site
inspection.

A straight route line from 817 to 818 through a wall is a product bug.

  ---------------------------------
  B. AUTHORITATIVE ROUTING SOURCE
  ---------------------------------

Use The Metropolitan Museum of Art’s CURRENT Floor 2 map / interactive
map as the authoritative reference for:

-   gallery placement;
-   public circulation;
-   doorway/pass-through connectivity;
-   temporary gallery closures;
-   step-free routing when relevant.

Relevant department:

19th- and Early 20th-Century European Paintings and Sculpture, Floor 2.

Hunt galleries:

810, 815, 816, 817, 818, 819, 821, 822, 824, 825

Nearby and intervening galleries may be included as navigation nodes
even when they contain no scavenger-hunt quest.

Do not guess an individual doorway from a flat room rectangle. If
doorway connectivity cannot be verified, store it as unknown and do not
route through it.

  -------------------------
  C. SEPARATE DATA MODELS
  -------------------------

Maintain at least these independent concepts:

1.  questOrder
2.  galleryNodes
3.  galleryConnections
4.  closureOverrides
5.  routeValidations

Example quest order:

export const questOrder = [ 810, 815, 816, 817, 818, 819, 821, 822, 824,
825,];

Gallery nodes:

interface GalleryNode { id: number | string; label: string; x: number;
y: number; isQuestGallery: boolean; floor: number; }

Verified physical connections:

interface GalleryConnection { id: string; from: number | string; to:
number | string; bidirectional: boolean; type: “doorway” | “passage” |
“corridor” | “stairs” | “elevator”; stepFree?: boolean; verified:
boolean; source?: string; verifiedAt?: string; }

Temporary closure override:

interface ClosureOverride { galleryId?: number | string; connectionId?:
string; status: “closed” | “restricted”; effectiveDate?: string; note?:
string; sourceUrl?: string; }

Route validation:

interface RouteValidation { fromQuestGallery: number; toQuestGallery:
number; path: Array<number | string>; verifiedOn?: string; verifiedBy:
“official-map” | “onsite”; notes?: string; }

Never put an edge into galleryConnections merely because it seems
plausible.

  -------------------
  D. ROUTING ENGINE
  -------------------

When a player finishes a quest:

1.  Read the current quest gallery.
2.  Read the next quest gallery from questOrder.
3.  Load verified galleryConnections.
4.  Apply closureOverrides.
5.  Remove unavailable nodes/edges.
6.  Find a valid walkable path.
7.  Render only the verified path edges.

A simple BFS or Dijkstra implementation is sufficient for MVP.

Do NOT: - route by Euclidean distance alone; - draw a straight line
between quest markers; - route through a wall; - route through
staff-only space; - silently use an unverified edge.

If no verified route exists, do not invent one.

Instead display:

NEXT MYSTERY: GALLERY XXX

Gallery routes can change. Use The Met’s current map or ask a guard for
the best way.

Actions:

OPEN THE MET’S OFFICIAL MAP I’M THERE — SHOW MY CLUE

  ---------------------------------
  E. CURRENT CLOSURES ARE DYNAMIC
  ---------------------------------

Gallery closures are operational data, not canonical game content.

As of the current Met closure information checked on October 21, 2026,
the museum’s page (last updated October 20) lists Galleries 813–814 as
temporarily closed in this department.

This must NOT be hard-coded as permanently true.

Before production deployment and ideally before a live game session,
check the current official Met closure page/map.

Model:

interface GalleryAvailability { galleryId: number; status: “open” |
“closed” | “unknown”; checkedAt?: string; sourceUrl?: string; }

If a QUEST gallery is closed: - mark the quest temporarily
unavailable; - do not direct the child into the closed gallery; - allow
the quest to be skipped without penalty; - preserve the canonical quest
for future use; - explain the situation in Parent Mode.

If an INTERMEDIATE routing gallery is closed: - remove it from
pathfinding; - find another VERIFIED path; - if none exists, use the
official-map/guard fallback.

Never alter a riddle because of a temporary closure.

  --------------
  F. MAP ASSET
  --------------

Do not copy or mechanically trace The Met’s published visitor map unless
usage rights explicitly permit that.

Create an original simplified SVG schematic based on verified current
spatial relationships.

The map should:

-   focus on the relevant Floor 2 area;
-   emphasize the 10 hunt galleries;
-   show necessary intervening navigation spaces;
-   include only verified connections;

The app’s schematic is a game/navigation aid, not an architectural plan

Do not request GPS.

  ------------------------
  G. ROUTE VISUALIZATION
  ------------------------

NOT:

817 → 818

The exact intervening nodes must be established from current
